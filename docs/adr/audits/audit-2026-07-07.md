## 🔴 Prioridad alta

### ADR-009 — Ausencia de CI que garantice el Quality Gate en la rama principal

Fuente: `docs/adr/ADR-009-quality-gate-shift-left.md`
Regla auditada: "Ningún cambio se integra a la rama principal sin pasar estas verificaciones" (lint, formato, pruebas + cobertura, E2E, Sonar).
Estado: ❌ Incumplido

Evidencias:
- ✔ Los hooks de Husky existen y están correctamente encadenados: `commit-msg` → commitlint, `pre-commit` → `lint-staged`, `pre-push` → `npm run test:coverage`.
- ✔ Los checks en sí funcionan: `npm run lint` no reporta errores y `npx vitest run --coverage` pasa con 100% de cobertura.
- ✖ No existe ningún pipeline de CI en el repositorio (`find . -iname "*.yml" -o -iname "*.yaml"` y `.github/` no arrojan resultados fuera de `node_modules`).
- ✖ Al depender solo de hooks locales, la regla es evitable con `git commit --no-verify` / `git push --no-verify`, con un clon que no ejecutó `npm install` (`prepare: husky` nunca corrió), o con un merge hecho directamente desde la interfaz de GitHub (que no dispara hooks locales de nadie).

Incumplimientos:
- Repositorio raíz — no hay `.github/workflows/` ni ninguna otra configuración de CI que re-ejecute lint, tests, cobertura, build o Sonar antes de integrar a `main`/`develop`.

Acción sugerida: Crear un pipeline de CI (p. ej. GitHub Actions, ya que el remoto es GitHub) que ejecute `npm run lint`, `npm run test:coverage`, `npm run build` y, cuando el Sonar real esté conectado, `npm run sonar`, como *required check* antes de poder mergear a `main`/`develop`. Esto convierte el Quality Gate de "confiado a la disciplina local" a "estructuralmente garantizado", cerrando el propio riesgo que el ADR ya anticipa en su sección de trade-offs.

## 🟡 Prioridad media

### ADR-005 — Código en `shared` sin ninguna feature consumidora

Fuente: `docs/adr/ADR-005-arquitectura-feature-based.md`
Regla auditada: el código transversal "solo se promueve a ese espacio compartido cuando es usado por más de una feature".
Estado: ⚠️ Parcialmente cumplido

Evidencias:
- ✔ La fitness function existente (`src/architecture/adr-005-feature-isolation.test.ts`) pasa: ninguna feature importa directamente de otra feature.
- ✔ `src/shared/styles/globals.css` y `src/shared/test/object-mother/` son cross-cutting legítimos (reset global de estilos e infraestructura de testing), no código de dominio anticipado.
- ✖ Actualmente solo existe una feature (`home`), y ni `src/shared/ui/checkbox.tsx` ni `src/shared/stores/task-store.ts` son importados por ella ni por ningún otro módulo de `src/features` (`grep -rn "shared/ui\|shared/stores\|@/shared" src/features src/app` solo encuentra el import de `globals.css`). Es decir, hoy tienen **cero** consumidores, no "más de una feature".

Incumplimientos:
- `src/shared/ui/checkbox.tsx` — componente construido sobre Base UI, sin ningún import desde `src/features/`.
- `src/shared/stores/task-store.ts` — store de Zustand, sin ningún import desde `src/features/`.

Acción sugerida: Si son código adelantado para la feature de gestión de tareas propuesta en `openspec/changes/gestion-completa-tareas/`, moverlos temporalmente a esa feature (`src/features/<feature>/`) y promoverlos a `shared` recién cuando una segunda feature los consuma; o, si el equipo prefiere mantenerlos en `shared` como base reutilizable intencional, dejar constancia explícita de la excepción (p. ej. en el propio ADR o en `.agents/MEMORY.md`).

### ADR-009 — Sonar Scanner sin conectar a un servidor real

Fuente: `docs/adr/ADR-009-quality-gate-shift-left.md`
Regla auditada: el Quality Gate incluye "Análisis de calidad de código (Sonar Scanner)".
Estado: ⚠️ Parcialmente cumplido

Evidencias:
- ✔ `sonar-project.properties` existe con `projectKey`, `sources`, `tests` e inclusiones/exclusiones correctamente configuradas, y el script `npm run sonar` está definido.
- ✖ El propio archivo se declara como scaffold: `sonar.organization=<pendiente>` está comentado y no hay `sonar.host.url` — sin uno de los dos, el scanner no tiene a dónde reportar. El comentario en el archivo lo reconoce explícitamente: *"Scaffold local — reemplazar con los valores reales al conectar un servidor Sonar"*.

Incumplimientos:
- `sonar-project.properties` — sin `sonar.organization` (SonarCloud) ni `sonar.host.url` (SonarQube self-hosted) configurados; `npm run sonar` no puede ejecutarse contra un servidor real todavía.

Acción sugerida: Conectar SonarCloud o una instancia SonarQube real (definir `sonar.organization` + `SONAR_TOKEN`, o `sonar.host.url`) e incorporar el paso al pipeline de CI sugerido en el hallazgo de Alta prioridad.

### Sugeridas (ADR apto sin fitness function)

**ADR-002 — Uso de Tailwind CSS como framework de presentación**
- Qué medir: que no se introduzcan otras soluciones de estilado (CSS Modules, styled-components, CSS-in-JS).
- Herramienta sugerida: script de grep en CI, o regla `dependency-cruiser`.
- Esbozo: fallar si aparece algún archivo `*.module.css` o un import de `styled-components`/`@emotion` bajo `src/`.

**ADR-003 — Uso de Base UI como librería de componentes**
- Qué medir: que no se agregue otra librería de componentes headless o con estilos propios (Radix, MUI, Chakra UI, Ant Design).
- Herramienta sugerida: script/test sobre `package.json` en CI.
- Esbozo: fallar si `dependencies`/`devDependencies` contienen alguno de esos paquetes.

**ADR-004 — Uso de Zustand para manejo de estado**
- Qué medir: que no se agregue otra librería de estado global (Redux, Recoil, Jotai, MobX).
- Herramienta sugerida: mismo patrón que ADR-003, script sobre `package.json`.
- Esbozo: fallar si `dependencies` contienen alguno de esos paquetes.

**ADR-005 — Arquitectura feature-based (extensión de la fitness function existente)**
- Qué medir: que todo módulo bajo `src/shared/**` tenga al menos una feature consumidora real (idealmente, que justifique estar en `shared` por tener más de una).
- Herramienta sugerida: extender `src/architecture/adr-005-feature-isolation.test.ts`.
- Esbozo: recorrer `src/shared/**` y, por cada módulo exportado, contar cuántas features distintas lo importan; fallar si el conteo es 0 (o advertir si es exactamente 1).

**ADR-008 — Uso de Playwright para las pruebas E2E**
- Qué medir: que no se agregue otra herramienta de automatización E2E (Cypress, Selenium, Puppeteer).
- Herramienta sugerida: script/test sobre `package.json`.
- Esbozo: fallar si `devDependencies` contienen alguno de esos paquetes.

**ADR-010 — Estrategia de branching GitFlow**
- Qué medir: que los nombres de rama sigan `feature/*|release/*|hotfix/*` (además de `main`/`develop`).
- Herramienta sugerida: hook `pre-push` de Husky o step de CI que valide el nombre de la rama actual.
- Esbozo: regex `^(main|develop|feature/|release/|hotfix/)` sobre el nombre de rama antes de permitir el push.
